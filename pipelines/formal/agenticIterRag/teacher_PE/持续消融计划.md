# SPAD Teacher 持续消融计划

日期：2026-07-10 18:23 CST

## 1. 当前维持策略

当前维持的生产候选是 `question-tail evidence-only`，对应本目录
`baseline_question_tail_evidence_only_v2` 变体。它保持现有 teacher system prompt，不使用
gold、不使用 thinking、不使用 few-shot，每个样本只调用一次 GLM-4.7-Flash。

User prompt 保留以下内容：

```text
Original question
Search evidence
  Round
    retrieved contents
      [rank] title
      passage
Original question to judge
```

相对现行 v2，它只做两项布局调整：

1. 不向 teacher 展示 actor 生成的 `sub_query`，避免 teacher 把检索动作误当成待回答问题。
2. 在所有 passage 后重申 Original question，使最终状态与原问题重新绑定。

仍保留首部问题、round、passage rank、title、完整 top-5 passage 和完整
`<reason><status><answer>` 输出。不得删除 title、只留 top-3、加入当前 237 条样本作为 few-shot，
也不得用多 prompt 投票作为默认 teacher。

## 2. 当前效果

最新一轮要求 Top 5 每个做 3 次全新推理。`question-tail evidence-only` 的 59 条 holdout 结果为：

| 指标 | 均值 | 最小值 | 最大值 |
| --- | ---: | ---: | ---: |
| I precision | 0.8556 | 0.8400 | 0.8750 |
| I recall | 0.8667 | 0.8400 | 0.9200 |
| I F1 | 0.8606 | 0.8400 | 0.8846 |
| XML parse rate | 1.0000 | 1.0000 | 1.0000 |

这是目前单 teacher 调用策略中最好的严格三重复均值。此前累计 6 次的均值为
`0.8545/0.8533/0.8530`，方向一致。单次 `0.920/0.920` 不能单独作为结论，因为 temperature=0
下仍观察到明显的 MoE/batch 调度波动。完整结果见
`REPLICA_STABILITY.md` 和 `RESULTS_INDEX.md`。

主要对照结论：

- 保留 sub_query 的 question-tail 三次均值为 `0.843/0.853`，低于当前候选。
- 去 title 的 question-tail 三次均值为 `0.849/0.827`，没有收益。
- 短 focused prompt 三次均值为 `0.883/0.787`，precision 更高但 recall、parse rate 下降。
- 5 路投票 dev 可到 `0.913/0.913`，但 holdout 退化且成本约 5 倍，不采用。
- gold-aware、critic/debate、one-token gate 和 thinking 均未形成更好的准确率/成本组合。

## 3. 当前最佳策略的两个口径

### 3.1 指标最佳

按独立 holdout、多次重复运行均值和格式稳定性选择，当前最佳仍是
`baseline_question_tail_evidence_only_v2`，即 `question-tail evidence-only`。它在某次 replica 上达到过
I precision/recall `0.920/0.920`，这是所有有效实验中的最高单次 holdout 观测之一；但同一 prompt
的历史 6 次结果存在 `0.808-0.920` 的明显波动，因此不能把 `0.920/0.920` 当作稳定能力。最新
cache-free 三重复均值为 `0.8556/0.8667`，I F1 `0.8606`；历史 6 次均值也支持相同排序。

五路投票曾在 dev 得到 `0.913/0.913`，但冻结后 holdout 只有 `0.905/0.760`，不属于泛化最佳方案。

### 3.2 综合时间后的最佳

综合准确率、重复稳定性、调用数、输出长度与格式成功率，最佳策略仍是
`question-tail evidence-only`：每个样本只调用 teacher 一次，不使用 thinking、gold、few-shot、critic
或投票，XML parse rate 为 `1.0`。最新三次全量运行中，237 条墙钟均值 `117.88s`，平均单请求
耗时 `7.71s`（单实例 16 并发负载下），平均 completion `83.1 tokens`；总输出量与当前 v2
baseline 基本同级。

Top 5 中纯速度最快的是 short-focused：237 条墙钟 `104.05s`、平均请求 `6.82s`、`53.6 tokens`。
但其 I recall 只有 `0.7867`，parse rate `0.9831`，不值得用约 11.5% 的请求耗时收益交换主指标和
格式可靠性。

one-token gate 更快，但 holdout I precision/recall 仅约 `0.792/0.760`；五路投票约增加到 5 次调用，
且没有 holdout 收益。因此前者只能算“纯速度最快”，后者只算“dev 分数较高”，都不是当前的
准确率/时间 Pareto 最优生产候选。

## 4. 下一步实施

### 阶段 A：注册生产候选

1. 在生产 prompt registry 增加明确版本名，例如
   `spad_teacher_evidence_status_answer_v3_question_tail_no_subquery`。
2. Builder 必须复用 v2 的 question、round、rank、title、passage，只删除 sub_query 并在末尾重复问题。
3. Stage1、Stage2 HTTP、offline batch 继续通过已修复的 `prompt_version` 透传选择版本。
4. 增加 snapshot test，逐字符验证 v3 messages；保留 v1/v2 以便回退。

在新版本正式注册前，不修改默认 v2，避免把实验变体直接变成生产默认值。

### 阶段 B：新数据泛化验证

1. 从 agent LLM 开始重新 rollout 200 条新数据，完整落盘 actor turns、sub-query、top-5 passages、
   teacher messages、raw XML、prompt version 和请求参数。
2. 在看 teacher 结果前冻结抽样和人工审计规则；新 200 条不得进入 few-shot。
3. 对 v2 baseline 与 v3 candidate 做 paired evaluation，至少独立运行 3 次，报告均值、范围和逐样本翻转。
4. 人工审计重点覆盖两类错误：false I（非 I 被判 I）和 missed I（I 被判 S/A）。
5. 若没有完整人工标签，不得把 gold alias 规则或旧 teacher 输出当作人工真值。

### 阶段 C：输出长度与 thinking

1. 在 v3 布局固定后，单独测试 `max_tokens=256` 与更短 reason 指令；准确率、parse 和截断率必须同时报告。
2. thinking 暂不作为默认。当前服务模板会把 thinking 写进 content，平均约 1095 tokens 且产生截断。
3. 只有后端能稳定分离 hidden reasoning 与 final XML 后，才重新测试 thinking，并报告单样本延迟。

### 阶段 D：训练影响验证

1. 用同一批 actor rollout 对 v2/v3 teacher reward 做离线重放，隔离 prompt 变化，不重新训练 actor。
2. 比较 teacher status 分布、bad-stop 奖励、answer F1、搜索轮数与零奖励比例。
3. 通过后再做小规模 Stage1 训练；不得直接用 500 样本全流程验证 prompt。

## 5. 选择与停止规则

- 主指标继续使用 I precision/recall；理想上限是双 0.98，但不是硬交付门槛。
- 候选选择基于独立 holdout 和重复运行均值，不挑最高 replica。
- parse rate 必须为 1.0；单次 teacher 调用优先，多调用策略必须证明显著收益才可进入生产。
- 每累计 10 个有效方案，在 `ABLATION_HISTORY.md` 增加一组方案、效果和反思。
- few-shot 禁止包含、改写或可识别地派生自当前评估数据的内容。
- 正式消融使用 `--disable-cache`，完成后必须确认 `run.json.cache_hits=0`；缓存复放永久排除。

## 6. 并行执行约束

离线消融应并行加速，但每个策略仍按单 teacher 调用设计。当前验证过的安全拓扑是 4 个 TP=2
replica，每个 replica 总并发不超过 16；同时跑多个策略时按每实例并发总和控制，不得因策略数量叠加
到 16 以上。运行期间检查 ready 状态、KV cache、请求错误和 OOM 日志。
