# AgenticIterRag 训练任务脚本记录

更新时间：2026-07-14

本文记录 `tasks/train_tasks/agenticIterRag/` 顶层现存 shell 入口的用途、配置组合、默认执行范围和使用风险。记录以当前工作区中的脚本及 YAML 为准，不反推历史 run 当时的配置；历史实验必须以对应 run 的 `final_config.yaml`、manifest 和代码哈希为准。

## 1. 目录约定

这些 shell 文件通常不直接写训练超参数，而是调用统一入口：

```text
scripts/agenticIterRag_v1/01_pipeline_launcher.sh
```

配置合并顺序为：

1. `--main-run-config` 加载顶层 manifest。
2. `--DATA_CONFIG`、`--PIPELINE_CONFIG`、`--RESOURCE_CONFIG`、`--AGENT_TRAINING_CONFIG` 等选择配置组。
3. `--OVERLAY_YAML` 按命令行出现顺序依次覆盖，后面的 overlay 优先级更高。
4. 脚本末尾的 `"$@"` 最后生效，可继续追加 overlay 或键值覆盖。

因此，判断一个任务不能只看 shell 文件名，必须同时读取它引用的所有 overlay。公共 base 或 overlay 被原地修改后，同一 shell 入口再次执行也可能产生不同训练语义。

`co_search_ablation` 是沿用至今的数据配置组名。引用该配置组不等于脚本本身是消融任务，也不应据此删除脚本。

## 3. AIR 离线链路和 reranker 入口

### 3.1 `run_00_AIR_v1_offline_example_task.sh`

用途：AgenticIterRag v1 离线两阶段完整示例。它展示如何组合完整配置组，不是当前 SPAD Qwen3-1.7B 主训练入口。

默认配置：

- 模型：`qwen3_4b`。
- pipeline：`offline_two_stage`。
- overlay：`configs/offline_two_stage_overlay.yaml`。
- 默认 stage 链：`train_agent -> generate_traces -> build_reranker_dataset -> train_llm_reranker -> infer_matrix`。
- 构造 reranker 数据时使用 recall top-50 候选，输出 VERL chat/GRPO 格式。
- 推理矩阵包含 origin/trained agent 与 original/trained reranker 的四组组合。

定位：配置组合范例和旧 AIR 全链路入口。实际运行前应先检查各 stage 的实现和输入 manifest 是否仍存在。

### 3.2 `run_260702a_AIR_v1_dataproduce.sh`

用途：只生产数据，不训练 agent 或 reranker。

默认行为：

- 从 `generate_traces` 开始，到 `build_reranker_dataset` 停止。
- 使用既有 Qwen3-4B agent checkpoint `.../global_step_79` 进行真实推理。
- 生成 canonical trajectory、reranker input dataset 和 GRPO train dataset。
- 不限制 `trace_max_samples`，CLI 固定 `infer_batch_size=96`、vLLM `gpu_memory_utilization=0.8`。
- 保留 full trace；overlay 内 `flush_every_n=10`。

定位：离线数据生产工具，不应计入“模型训练任务”。

### 3.3 `run_260703a_AIR_v1_llm_agent_training.sh`

用途：早期命名为 LLM agent training 的入口，但脚本注释称其为 “LLM reranker branch GRPO”。脚本同时选择 `RERANKER_TRAINING_CONFIG=llm_reranker_grpo_branch`，命名与注释并不一致。

阻塞项：引用的 `configs/agent_training_v1_overlay.yaml` 当前不存在。由于决定 stage 范围和实验差异的 overlay 缺失，无法可靠确认它原本训练 agent 还是 reranker，也不可直接执行。

定位：仅保留作历史入口索引。恢复前必须先从历史 run 的 final config 或备份还原 overlay，不能凭文件名补写。

### 3.4 `run_260703a_AIR_v1_llm_reranker_training.sh`

用途：使用已经构造好的 branch dataset 做 LLM reranker GRPO，并生成 service bundle。

默认配置：

- 模型：Qwen3-4B reranker 分支。
- overlay：`configs/llm_reranker_training_overlay.yaml`。
- 从 `train_llm_reranker` 开始，到 `build_service_bundle` 停止。
- 默认读取全量 branch dataset，但只执行 Stage1 format 的 1 个训练 step。
- `stage2_agentic` 关闭；reward 为 `answer_reward`。
- 输出第 1 step checkpoint 和 service bundle。

定位：早期真实 VERL 1-step 链路验证，不是完整收敛训练。

### 3.5 `run_260703b_AIR_v1_from_dataprod_to_reranker_training.sh`

用途：从既有 trajectory 构造 endpoint branch dataset，筛选 hard/improvable 子集，再训练 Stage2 agentic LLM reranker。

overlay 顺序：

1. `configs/endpoint_hard_short_reason_base_overlay.yaml`
2. `configs/endpoint_hard_short_reason_answer_evidence_w02_n8_1p5epoch_overlay.yaml`

默认配置：

- 从 `build_reranker_branch_dataset` 开始，到 `train_llm_reranker` 停止。
- endpoint 候选 top-50，展示 top-5，使用 short-reason prompt。
- hard filter 要求 top-50 命中、top-5 未命中且 baseline reward 为 0。
- Stage1 format 关闭，Stage2 agentic 开启。
- reward 子策略：`answer_reward_plus_evidence_hit`，证据命中权重 `0.2`。
- rollout 每题 `n=8`，训练 `1.5 epoch`。
- CLI 再固定 `data.trace_max_samples=-1`。

定位：endpoint hard subset 的专项正式 reranker 训练入口。

### 4.3 `run_260709f_AIR_spad_qwen3_1_7b_glm47_formal.sh`

用途：SPAD Qwen3-1.7B 三阶段基准入口。

当前默认解析结果：

- 数据：Stage1 和 Stage2 各 512 条；Stage1 一轮约 8 steps。
- Stage1 `search_policy_rl`：VERL GRPO，reward 为 `spad_em_teacher_backoff`，每题 8 条 rollout。

定位：SPAD 三阶段基础模板。若后续默认只做 Stage1，应额外叠加明确关闭 Stage2/Stage3 的 overlay，不要直接运行本脚本期待“只跑 Stage1”。

## 5. Gold Token-F1 reward 的当前实现说明

实现文件：

```text
AgenticIterRag/agentic_iter_rag/agent_training/spad/rewards/search_policy_teacher_reward_gold_match_bonus.py
```

它通过组合 stable `spad_em_teacher_backoff` 实现，而不是修改旧 reward：

1. 先完整计算 stable base reward。
2. 仅在整组 Actor EM 为 0、Teacher 已调用且成功解析、Actor 有合法闭合答案、Teacher 证据状态受支持时计算 bonus。
3. Teacher answer 与所有 gold alias 分别计算 legacy token-F1，取最大值。
4. `final_reward = base_reward + 0.1 * max_token_f1`。

文件名中的 `gold_match_bonus` 是早期命名；当前实际不是严格 EM match，而是 token-F1 bonus。

## 7. 执行前检查清单

1. 确认脚本引用的每个 overlay 都存在；当前有 3 个历史入口因 overlay 缺失而不可运行。
2. 检查 overlay 合并顺序，特别是 formal、scale、reward 三层组合。
3. 检查最终 `resume_from_sub_stage`、`stop_after_sub_stage` 和各 sub-stage 的 `enabled`，不要仅凭文件名推断是否只跑 Stage1。
4. 检查 `train_files`、`train_max_samples`、`total_training_steps`、`data_seed` 和 `save_freq`。
5. 检查 reward 类型、reward 实现代码版本、`norm_adv_by_std_in_grpo` 和 `stream_group_max_inflight`。
6. 正式运行后，以 run 目录中的最终合并配置为唯一可复现实验依据。
